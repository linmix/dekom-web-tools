# DEKOM SEO Scan and Review Workflow

## Purpose

This workflow supports two related SEO tasks:

1. **Initial SEO review**
   
   - extract current SEO-relevant content from the DEKOM websites;
   - group pages into logical review batches;
   - review SEO titles and meta descriptions with ChatGPT;
   - store approved editorial decisions independently from the live website;
   - implement approved changes in Pimcore.

2. **Ongoing SEO maintenance**
   
   - rescan the websites after pages or metadata change;
   - compare current live metadata with previously approved editorial decisions;
   - identify whether approved changes are live, pending, or have diverged;
   - compare follower sites with their authoritative language site;
   - identify page-structure differences between paired sites;
   - revisit SEO when content or SEO requirements change.

The live website is **not** the editorial source of truth.

The intended SEO value is stored separately from whatever currently happens to be published.

For each language, one site is authoritative for editorial decisions:

```textile
Dutch:   nl-nl
English: en-nl
```

The corresponding follower sites inherit those decisions:

```textile
nl-nl → nl-be
en-nl → en-gb
```

```textile
4. Ask ChatGPT to review one batch
5. Decide KEEP / ACCEPT / CUSTOM
```


```textile
nl-be   follows nl-nl
en-gb   follows en-nl
```

Editorial decisions are recorded only for the authoritative sites.

Follower sites inherit the corresponding authoritative `finalValue` and are used for implementation comparison and page-parity checks.

## 4. Make editorial decisions

For every page, title and description decisions are made independently.

Use:

```textile
KEEP
ACCEPT
CUSTOM
```

Examples:

```textile
1 KEEP

2 title ACCEPT, description KEEP

3 title CUSTOM: Zoom Rooms voor hybride vergaderruimtes
  description ACCEPT
```

Meaning:

```textile
KEEP
    Keep the value that was present when the page was reviewed.

ACCEPT
    Use ChatGPT's proposed value.

CUSTOM
    Use a different final value chosen during review.
```

For a `CUSTOM` decision, the original `proposedValue` remains stored and the chosen custom value becomes `finalValue`.

Do not manually edit `decisions.json` or `decisions.md`.

---

## 5. Save the review with `applySeoReview.js`

After the editorial decisions for a batch are settled, ChatGPT generates one complete PowerShell payload.

Editorial decisions must always be saved against the authoritative site.

For Dutch reviews, the payload ends with:

```powershell
node .\modules\applySeoReview.js nl-nl --apply
```

For English reviews:

```powershell
node .\modules\applySeoReview.js en-nl --apply
```

A typical payload has this form:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)

@'
{
  "pages": [
    ...
  ]
}
'@ | node .\modules\applySeoReview.js nl-nl --apply
```

The UTF-8 output encoding line is required when running these payloads in
Windows PowerShell 5.1. Without it, characters outside the default console
encoding, such as en dashes, em dashes, curly quotes and accented characters,
may be replaced with `?` before the JSON reaches Node.js.

ChatGPT-generated editorial apply payloads must therefore always begin with:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)   
```

Normally, the user should not create or edit this JSON manually.

Copy the complete PowerShell block produced by ChatGPT and run it from:

```textile
C:\Users\linmix\DEKOM-web
```

`applySeoReview.js` updates the authoritative editorial state in:

```textile
SEO\<leader>\review\decisions.json
SEO\<leader>\review\decisions.md
```

For Dutch:

```textile
SEO\nl-nl\review\decisions.json
SEO\nl-nl\review\decisions.md
```

For English:

```textile
SEO\en-nl\review\decisions.json
SEO\en-nl\review\decisions.md
```

`decisions.json` is the authoritative editorial source of truth.

`decisions.md` is the generated human-readable leader review ledger.

Follower sites do not maintain their own `decisions.json`.

Their generated:

```textile
SEO\<follower>\review\decisions.md
```

is an implementation report that compares the follower site with the authoritative leader `finalValue`.

The tool rejects attempts to save editorial decisions directly against follower sites such as `nl-be` or `en-gb`.

Do not manually edit `decisions.json` or `decisions.md`.

## 6. Check recorded review state

Leader and follower sites have different report purposes.

For an authoritative site, inspect:

```textile
SEO\<leader>\review\decisions.md
```

For Dutch:

```powershell
Get-Content .\SEO\nl-nl\review\decisions.md -Encoding utf8
```

For English:

```powershell
Get-Content .\SEO\en-nl\review\decisions.md -Encoding utf8
```

The leader report shows, for every reviewed component:

```textile
reviewed value
proposed value
final value
current live value
implementation status
```

Leader implementation status can be:

```textile
LIVE
PENDING
MISMATCH
```

Meaning:

```textile
LIVE
    The current live value matches the approved finalValue.

PENDING
    The live value still matches the value seen during review,
    while the approved finalValue is different.

MISMATCH
    The live value matches neither the reviewed value
    nor the approved finalValue.
```

For a follower site, inspect:

```textile
SEO\<follower>\review\decisions.md
```

For Dutch:

```powershell
Get-Content .\SEO\nl-be\review\decisions.md -Encoding utf8
```

For English:

```powershell
Get-Content .\SEO\en-gb\review\decisions.md -Encoding utf8
```

The follower report compares the follower site with the authoritative leader `finalValue`.

Follower component status can be:

```textile
MATCH
DIFFERS
PAGE MISSING
```

Meaning:

```textile
MATCH
    The follower value matches the authoritative finalValue.

DIFFERS
    The follower value does not match the authoritative finalValue.

PAGE MISSING
    A reviewed authoritative page has no corresponding page
    in the follower index.
```

The follower report also includes complete site parity:

```textile
Leader-only pages
Follower-only pages
```

These parity checks compare the complete leader and follower indexes and are independent of which pages have already been reviewed.

Do not edit either report manually.

Both are generated from the current SEO index and authoritative review state.

---

## 7. Implement approved changes in Pimcore

It is normally preferable to review an entire logical batch before implementing changes.

Typical workflow:

```textile
review Zoom batch
   ↓
save all Zoom decisions
   ↓
implement approved Zoom metadata in Pimcore
```

The saved editorial decisions do not depend on immediate Pimcore implementation.

The value that should ultimately be implemented is the stored:

```textile
finalValue
```

The live website must not replace the saved editorial decision as the source of truth.

For paired sites, implement the appropriate equivalent metadata on both sites.

The authoritative site owns the editorial decision; the follower is expected to match it where the pages correspond.

---

## 8. Verify implementation later

After approved metadata has been implemented in Pimcore, refresh both the authoritative site and its follower so the live website state can be checked against the saved editorial decisions.

For Dutch:

```powershell
node .\seo-scan.js nl-nl --refresh
node .\seo-scan.js nl-be --refresh
```

For English:

```powershell
node .\seo-scan.js en-nl --refresh
node .\seo-scan.js en-gb --refresh
```

The authoritative site compares current live metadata with:

```textile
SEO\<leader>\review\decisions.json
```

and regenerates:

```textile
SEO\<leader>\review\decisions.md
```

Expected leader progression:

```textile
PENDING
   ↓
change implemented in Pimcore
   ↓
fresh --refresh scan
   ↓
LIVE
```

If the current live value matches neither the value originally seen during review nor the approved `finalValue`, the leader status becomes:

```textile
MISMATCH
```

The follower site does not have its own editorial `decisions.json`.

Instead, it reads the authoritative leader decisions and regenerates:

```textile
SEO\<follower>\review\decisions.md
```

The follower report shows whether each reviewed title and description is:

```textile
MATCH
DIFFERS
PAGE MISSING
```

It also performs full site-level parity checks and reports:

```textile
Leader-only pages
Follower-only pages
```

Implementation verification therefore has two separate purposes:

```textile
Leader
    Did the live authoritative site implement the approved editorial finalValue?

Follower
    Does the follower site match the authoritative finalValue,
    and does its page structure remain aligned with the leader?
```

The authoritative `finalValue` remains the editorial source of truth even if either live website currently differs from it.

# High-Level Workflow

The workflow separates editorial review from follower-site implementation checking.

For each language, one authoritative site owns the editorial decisions:

```textile
Dutch:   nl-nl
English: en-nl
```

Follower sites inherit those decisions:

```textile
nl-nl → nl-be
en-nl → en-gb
```

The authoritative workflow is:

```textile
Authoritative website
   ↓
Sitemap
   ↓
URL filtering
   ↓
cache\<leader>\urls-check.json
   ↓
Downloaded page HTML
   ↓
SEO extraction
   ↓
SEO\<leader>\index.json
   ↓
Batch generation
   ↓
SEO\<leader>\batches\
   ↓
ChatGPT editorial review
   ↓
KEEP / ACCEPT / CUSTOM
   ↓
SEO\<leader>\review\decisions.json
   ↓
approved finalValue
   ↓
Pimcore implementation
   ↓
fresh leader scan
   ↓
LIVE / PENDING / MISMATCH
```

The follower workflow is separate:

```textile
Follower website
   ↓
fresh or existing SEO index
   ↓
SEO\<follower>\index.json
   ↓
read authoritative decisions from:
SEO\<leader>\review\decisions.json
   ↓
compare follower metadata with leader finalValue
   ↓
SEO\<follower>\review\decisions.md
   ↓
MATCH / DIFFERS / PAGE MISSING
   ↓
full site parity:
Leader-only pages
Follower-only pages
```

The authoritative `decisions.json` is the editorial source of truth.

The live website is never treated as the editorial source of truth.

Follower sites do not maintain their own editorial decision JSON.

For Dutch, the authoritative state is:

```textile
SEO\nl-nl\review\decisions.json
```

and the follower implementation report is:

```textile
SEO\nl-be\review\decisions.md
```

For English, the authoritative state is:

```textile
SEO\en-nl\review\decisions.json
```

and the follower implementation report is:

```textile
SEO\en-gb\review\decisions.md
```

## Rebuilding review batches

Review batches are normally rebuilt as part of `--refresh`.

`--existing` deliberately does not rebuild them.

This avoids rewriting hundreds of generated SEO files when only review or implementation status needs to be refreshed.

If grouping logic changes and the website itself does not need to be refreshed, batch rebuilding should be invoked explicitly rather than becoming an automatic side effect of `--existing`.

No separate user-facing batch-rebuild command is currently defined.

# `--existing` versus `--refresh`

## `--existing`

`--existing` assumes that the required generated SEO data is already present.

It performs:

```textile
existing SEO\<site>\index.json
   ↓
refresh leader review report
or
refresh follower implementation/parity report
   ↓
Google Drive sync
```

It does not:

```textile
load the sitemap
redownload pages
re-extract SEO data
rebuild review batches
```

This mode is intended to be fast and should normally touch only the files required to refresh review status.

---

## `--refresh`

`--refresh` performs the complete website-data refresh.

Conceptually:

```textile
website sitemap
   ↓
load URLs
   ↓
apply site filters
   ↓
write current SEO URL scope
   ↓
clear old cached page data as required
   ↓
download current selected pages
   ↓
rebuild URL map
   ↓
extract SEO data
   ↓
SEO\<site>\index.json
   ↓
build review batches
   ↓
refresh leader or follower review report
   ↓
Google Drive sync
```

Use this mode whenever the current live state matters.

# Meaning of the Cache Files

## `urls-all.json`

Contains URLs discovered during the sitemap-processing stage before the final SEO review scope is applied.

It is not the authoritative list of pages for SEO review.

---

## `urls-check.json`

This is the authoritative URL scope for SEO review.

Batch generation and SEO review scope must ultimately be based on:

```textile
cache\<site>\urls-check.json
```

Do not substitute `urls-all.json` when determining which pages belong in the SEO review.

---

## `urls-full.json`

Contains the broader URL data used during the scan process.

It supports processing but is not the editorial review scope.

---

## `url-map.json`

Maps site URLs to their locally stored page representations.

It supports extraction and regeneration of SEO data.

# Leader Review Structure

For an authoritative site:

```textile
SEO\<leader>\review\decisions.json
SEO\<leader>\review\decisions.md
```

`decisions.json` is authoritative.

It stores the editorial decisions independently of the current live website.

For each reviewed title or description, the important conceptual fields are:

```textile
decision
reviewedValue
proposedValue
finalValue
reviewedAt
```

`reviewedValue` records what was present when the decision was made.

`proposedValue` records the replacement proposed during review.

`finalValue` records the editorial result that should ultimately be live.

For a `KEEP` decision:

```textile
finalValue = reviewedValue
```

For an `ACCEPT` decision:

```textile
finalValue = proposedValue
```

For a `CUSTOM` decision:

```textile
proposedValue remains preserved
finalValue = the chosen custom value
```

The leader Markdown report is generated from this state.

Do not manually edit either file.

---

# Follower Review Structure

Follower sites do not maintain an editorial `decisions.json`.

They generate only the human-readable implementation report:

```textile
SEO\<follower>\review\decisions.md
```

That report reads the authoritative decisions from:

```textile
SEO\<leader>\review\decisions.json
```

and compares them with:

```textile
SEO\<follower>\index.json
```

It also compares the complete follower index with the complete leader index for page parity.

This provides two checks:

```textile
Metadata implementation
Page structure parity
```

---

# Review Status Logic

## Authoritative site

Leader status is evaluated per title and description.

Possible states:

```textile
LIVE
PENDING
MISMATCH
```

### LIVE

The current live value matches `finalValue`.

### PENDING

The current live value still matches `reviewedValue`, while `finalValue` is different.

This normally means the approved change has not yet been implemented.

### MISMATCH

The current live value matches neither the original `reviewedValue` nor the approved `finalValue`.

This normally means the page changed outside the recorded editorial decision.

---

## Follower site

Follower status is evaluated against the leader `finalValue`.

Possible states:

```textile
MATCH
DIFFERS
PAGE MISSING
```

### MATCH

The follower value matches the authoritative `finalValue`.

### DIFFERS

The follower value does not match the authoritative `finalValue`.

### PAGE MISSING

A reviewed leader page has no corresponding follower page.

---

# Page Parity

Follower reports also compare the complete leader and follower page indexes.

The report identifies:

```textile
Leader-only pages
Follower-only pages
```

A leader-only page exists in the authoritative site index but not in the follower index.

A follower-only page exists in the follower index but not in the authoritative site index.

These checks cover the complete site indexes, not only pages that already have SEO review decisions.

Page differences are therefore visible even before a page has been reviewed editorially.

# SEO Title Rules

Pimcore automatically appends:

```textile
 · DEKOM
```

Do not add this suffix manually.

The suffix occupies 8 characters.

Target the complete rendered title at approximately:

```textile
50–60 characters
```

The editable title should therefore normally be approximately:

```textile
42–52 characters
```

Editable titles above roughly 57 characters should be exceptional because they generate rendered titles of approximately 65 characters or more.

When reviewing titles, report both:

```textile
editable character count
rendered character count including " · DEKOM"
```

For the current title, count the complete published HTML title as captured by the scan. For a proposed editable title, append ` · DEKOM` once when calculating the expected rendered count. Label both counts in batch reviews and reports. In older scan output, `Title length` and `titleLength` refer to the editable title.

### Advisory pixel-width review

Measure the complete rendered title, including ` · DEKOM`, using Screaming Frog SEO Spider’s `Title 1 Pixel Width` or the desktop SERP Snippet preview. Use 561 px as the DEKOM audit review trigger. At or above that width, preview the snippet and check whether important wording might be truncated. Record pixel width separately from both character counts. Preserve approved titles unless the language leader approves an editorial change.
